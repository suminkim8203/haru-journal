# T07 인증 구현 설명서 — 검증 중

요약: 기존 Haru에 Supabase Auth와 서버의 계정별 자료 접근 검사를 연결했다. 실제 HTTP로 확인한 결과와 로컬 테스트를 구분한다. 사용자 실제 5일 기록 등 남은 증거가 있으므로 이 문서는 최종 제출본이 아니다.

## ① 무엇으로 붙였나

- 방식: 인증 서비스. NAS의 Supabase Auth v2.196.0, 앱 SDK `@supabase/supabase-js` 2.116.0. 설치 조회는 [설정 기록](auth-readonly-2026-09-21.json), 앱 버전은 `web/package-lock.json`을 기준으로 한다.
- 이메일·비밀번호 회원가입, 이메일 6자리 코드 확인, 비밀번호 로그인, 로그아웃, 이메일 확인을 통한 비밀번호 재설정을 제공한다. 메일은 Resend SMTP를 통해 발송하며 사용자가 실제 수신·로그인을 확인했다. 과거 설정 기록의 `smtpDeliveryVerified: false`는 당시 상태다.
- 브라우저는 토큰을 전달하고, 서버는 서명뿐 아니라 실제 Auth 세션의 존재·소유자·기한·비밀번호 인증 여부를 검사한다. 다이어리 접근 세션 상한은 생성 후 7일이며 `not_after`가 더 이르면 그 기한을 적용한다. 이것을 개별 JWT의 만료시간과 같은 의미로 설명하지 않는다.
- 비밀번호 해시 생성·검증은 Supabase Auth의 bcrypt에 맡긴다. [시험 계정 DB 관찰](PASSWORD-HASH-READONLY.md)에서 같은 비밀번호의 서로 다른 60자 해시와 비용 값 10을 확인했다.
- 이어 사용한 T06은 [고정 제출 기준](T06-BASELINE.md)이다. 기존 자료는 본인 계정에 이전했고 사용자가 로그인 후 조회를 확인했다.

## ② 왜 그걸 골랐나

기존 데이터베이스가 Supabase이므로 Auth의 계정 식별자와 DB 권한 검사를 연결할 수 있다. 비밀번호 보관·인증번호 검증을 직접 구현하지 않고 검증된 구성요소에 맡기면서, 로그아웃 즉시 차단 같은 과제 조건은 서버 경계에서 보완했다. bcrypt 역시 앱이 별도 암호화 알고리즘을 만들지 않고 Auth가 지원하는 방식을 사용한다.

대안은 Spring 기반 별도 인증 서버였다. 현재 프로젝트에서 인증용 서버와 세션·계정 동기화 운영을 추가해야 하므로 선택하지 않았다. Google·Kakao 간편 로그인도 이번 범위에는 넣지 않았다. 이는 서비스가 일반적으로 지원하는 기능과 현재 앱이 제공하는 기능을 구분한 결정이다.

## ③ 어디를 어떻게 고쳤나

저장소 루트 기준 경로다. UI에서 숨기는 것과 서버에서 접근을 차단하는 것은 별개다.

| 흐름 | 입력·실행 주체·검증·결과 | 소스 |
|---|---|---|
| 회원가입 | 사용자가 이메일·비밀번호 입력 → Auth가 계정 생성 요청 처리 → 메일 코드 발송 | `web/src/components/auth-form.tsx`의 `signUp`, `web/supabase/functions/auth-guard/index.ts` |
| 이메일 확인 | 사용자가 6자리 코드 입력 → Auth가 signup 코드 검증 → 확인 세션을 정리하고 비밀번호 로그인으로 이동 | 같은 컴포넌트의 `verifyOtp`와 `signOut` |
| 로그인 | 이메일·비밀번호 → Auth 검증 → 앱이 계정 상태와 자료 접근 권한 확인. 없는 이메일/틀린 비밀번호 안내는 동일 | `auth-form.tsx`, `web/src/components/private-journal.tsx` |
| 로그아웃 | 앱이 Auth 로그아웃 요청 → 세션 종료 → 이전 토큰으로 자료 요청해도 서버가 세션 부재를 거절 | `private-journal.tsx`, `web/supabase/staged-t07/01_session_boundary.sql` |
| 자료 조회·저장 | SDK가 인증값을 전달 → 서버가 현재 계정의 다이어리를 결정 → 대상 자료의 소유 관계 확인 후 처리 | `web/src/lib/storage.ts`, `02_private_rpc_cutover.sql`, `03_private_read.sql` |
| 비밀번호 재설정 | 로그인 화면에서 이메일 입력 → recovery 코드 확인 → 새 비밀번호 입력 → Auth 저장 및 전체 로그아웃 | `auth-form.tsx`, `05_password_revocation.sql` |

재설정의 `updateUser({password})`는 이메일 확인을 마친 복구 흐름에서 호출한다. 별도의 로그인 상태 비밀번호 변경 화면이나 초대·최초 비밀번호 설정 화면을 구현했다고 주장하지 않는다. 이전 비밀번호와 같은 값이면 현재 인증을 유지하고 다른 비밀번호를 입력하도록 안내한다.

`02_private_rpc_cutover.sql`은 클라이언트가 보낸 소유자 ID를 신뢰하지 않고, 계획·할 일·실행 기록 등 참조 대상의 소유 관계를 변경 전에 확인한다. 공개 직접 접근 권한도 제한한다. `05_password_revocation.sql`은 비밀번호 해시 변경 시각 이전 세션의 다이어리 접근을 차단한다.

계정 화면은 `/account.html`, 탈퇴 화면은 `/account/deletion.html`이다. [7일 탈퇴 정책](ACCOUNT-DELETION.md)에 따라 유예 중 자료를 차단하고 명시적 취소만 허용한다. 본인 실제 계정을 삭제해 시험하지 않았다.

## ④ 안 열리는 것을 확인한 기록

| 확인 묶음 | 성공과 거절 | 증거와 한계 |
|---|---|---|
| 비로그인 접근 | 로그인 snapshot 200 / 익명 snapshot 401 | [실제 요청·응답](evidence/private-http-2026-09-22.json). 비로그인 페이지도 로그인 화면 표시 확인 |
| 로그아웃 후 재사용 | 같은 `POST /rest/v1/rpc/haru_snapshot`, 같은 토큰·본문: 로그아웃 전 200 / 후 401 | 위 파일 `before logout`, `same token after logout` |
| 다른 계정 자료 | A/B 자신의 조회 각 200 / A→B와 B→A 조회·수정·삭제 모두 404 | 위 파일에 6개 거절. 목록 foreignCount=0, 반대편 snapshot 불변. 수정·삭제의 정상 성공 요청과 나란히 정리할 추가 증거는 남아 있음 |
| 소유자 위조 | 로컬 DB 검사에서 헤더·본문에 상대 소유자 ID를 넣어도 상대 자료 불변 | `web/tests/private-rpc.test.ts`. 실제 HTTP URL·헤더·본문 위조 증거를 대체하지 않음 |
| 비밀번호 재설정 후 재사용 | 같은 토큰·POST snapshot·본문으로 재설정 전 200 / 후 401. 로그아웃 호출 이전에 검사 | [2026-09-23 실제 HTTP 증거](evidence/password-reset-http-2026-09-23.json). 이전 비밀번호 로그인 400, 새 비밀번호 세션 조회 200. 복구 코드는 시험용 관리자 API로 생성했으므로 메일 전달 검증은 아님 |

추가 확인:

- 탈퇴 시험 계정: 신청 전 조회 성공 → 신청 후 이전 토큰 401 → 다시 로그인한 유예 계정의 자료 요청 423 → 명시적 취소 후 복원. [HTTP 기록](evidence/deletion-http-2026-09-22.json).
- 2026-09-23 소유자 위조·탈퇴·인증 경계 관련 로컬 테스트 5개 통과. 실행 명령: `node --experimental-strip-types --test tests/private-rpc.test.ts tests/account-deletion.test.ts tests/auth-boundary.test.ts` (`web` 폴더).
- [공개 비밀 형식 검사](evidence/public-secret-scan.json): 추적 파일·도달 가능한 Git 이력·정적 빌드에서 특정 비밀키/JWT 형식 탐지. 탐지 0건은 일반 비밀번호나 서버 로그까지 안전하다는 뜻이 아니다. 검사 도구는 `scripts/check-public-secrets.py`다.
- 저장 해시 전체 예시, 실제 로그인 요청·응답 및 서버 로그의 원문 부재, 전체 내보내기 파일의 다운로드·내용 검증은 추가 증거가 필요하다.

## ⑤ AI와 나

- AI에게 맡긴 일: 인증 연결·DB 경계·화면 구현, 자동 검사, 요청·응답 정리, 문서 초안.
- 사용자가 직접 판단한 일: 기존 디자인 유지, 이메일 인증과 재설정 흐름, 비밀번호 조건, 계정 화면 분리, 7일 탈퇴 유예, 5일 관찰 질문·지표·규칙 승인. 메일 수신·로그인·기존 자료 조회도 직접 확인했다.
- AI 제안을 따르지 않은 일: 12자 비밀번호 제안을 8자 이상·공백 금지로 수정했고, 로그인 화면 외의 별도 비밀번호 변경 UI와 본문에 끼어든 계정 조작 섹션을 지적해 변경했다.

AI가 수행한 427초의 개발 검증을 사용자의 실제 1일차로 간주하지 않는다. [5일 관찰표](FIVE-DAY-STUDY.md)는 사용자 실제 활동이 확인될 때만 채운다. 3일차 전 규칙 변경도 과거 날짜로 만들어 넣지 않는다.

## ⑥ 아직 못 막은 것·검증하지 못한 것

- 브라우저에 지속 저장되는 인증값은 XSS에 노출될 수 있다. 이메일 코드만으로 모든 클라이언트 공격을 막는 것은 아니다.
- 이메일·목적별 제한 로직이 있지만 운영 환경의 분산 IP 공격까지 차단하는지 검증하지 않았다. 한 종류의 제한만으로 무차별 대입이 해결됐다고 말하지 않는다.
- 수동 외부 백업의 복구까지 자동으로 삭제 계정 부활을 방지하는 연동은 없다. 복구 시 삭제 이력을 재적용하기 전 공개하지 않는 절차가 필요하다.
- 실제 168시간 경과 후 삭제 관찰은 아직이다. 시간 경계 테스트와 실제 일주일 운영 관찰은 구분한다.
- 증거가 없는 항목은 구현 유무와 별개로 미검증이다. 사용자 5일 기록·규칙 변경·화면 합계 및 평균 대조를 완료하기 전에는 제출 완료로 표시하지 않는다.

## 짧은 확인 방법 — 초안

1. 어디로 가나요: https://haruleaf.com/ 및 공개 소스 저장소.
2. 무엇을 하나요: 시크릿 창으로 열기 → 로그인 화면 확인 → 설명서의 마스킹된 성공/거절 요청 비교. 심사자에게 실제 계정 비밀번호를 제공하지 않는다.
3. 무엇이 보이면 통과인가요: 개인 자료가 첫 화면에 없고, 계정 경계를 넘은 요청과 로그아웃 후 동일 인증값 요청이 거절되는 증거가 있다.
4. 안 될 때는 무엇이 보이나요: 인증 실패는 일반 안내, 기한이 끝난 세션의 자료 요청은 401, 다른 계정의 대상 요청은 404. 아직 없는 증거는 위 표에 미검증으로 표시한다.
