# 월간 형광펜 팔레트 수정 — 2026-09-29

요약: 월간 계획 기간 띠가 승인된 ‘04 푸른 주석’ 다섯 색과 달랐던 원인을 수정했다. 첫 배포는 공개 인증 연결 설정이 빠져 브라우저가 열리지 않는 장애를 일으켰다. 즉시 직전 릴리스로 복구했고, 설정 검사와 실제 브라우저 검증을 추가한 새 릴리스로 다시 배포했다. DB 자료·인증 정책·계획 배치 방식은 변경하지 않았다.

## 원인과 수정

- 기존 `web/src/app/globals.css`는 주황색 `highlight-felt-02.webp` 한 장에 `hue-rotate`와 `saturate` 필터를 적용했다. 다섯 색 이름을 사용했지만 승인한 실제 색값은 아니었다.
- 같은 이미지의 불규칙한 알파 질감은 마스크로 유지하고, 색은 `#C79E8C`, `#BDB77E`, `#9FBBAF`, `#8EAFC3`, `#AAA9C5`를 직접 지정했다. 획의 불투명도는 승인된 46% 그대로다. 따라서 지면에 합성된 최종 픽셀은 원색 HEX보다 밝다.
- 계획 하나에는 계획 ID에 따라 결정되는 색 하나를 안정적으로 적용한다. 색만으로 계획을 식별하지 않도록 계획명을 계속 표시한다.

## 첫 배포 오류와 복구

- 소스 커밋 `1b636cd`의 첫 정적 빌드는 `NEXT_PUBLIC_HARU_PRIVATE=1`을 넣었지만 `NEXT_PUBLIC_SUPABASE_URL`과 `NEXT_PUBLIC_SUPABASE_ANON_KEY`를 넣지 않았다. 빌드 스크립트는 개인 화면 문구만 검사해 통과시켰다. `t07-palette-private-1b636cd`를 운영에 올리자 HTTP 200과 컨테이너 `healthy`에도 불구하고 브라우저의 인증 클라이언트가 `인증 연결 설정을 확인해 주세요.` 오류를 내며 화면을 열지 못했다.
- 사용자의 접속 실패 제보 뒤 브라우저 콘솔에서 이 오류를 확인하고 직전 정상 릴리스 `t07-visual-private-d0aed89`로 되돌렸다. 기본 주소에서 기존 기록이 다시 표시됨을 확인했다. 잘못된 릴리스에는 `DO_NOT_DEPLOY`를 표시했다.
- 사용자가 본 HTML과 `paper-fiber-subtle.webp`의 304는 캐시 재검증 응답이며 장애 원인이 아니었다. 이 판단은 인증 클라이언트 오류와 정상 릴리스 복구 결과에 근거한다.

## 수정 후 재배포와 확인

- `web/scripts/build-static.mjs`에 공개 Supabase URL·anon key가 둘 다 없으면 종료 코드 2로 실패하는 검사를 추가했다(커밋 `f96719b`). 설정값을 출력하지 않고 기존 공식 웹 설정에서 읽어 개인 보호 모드로 다시 빌드했다.
- 새 빌드를 운영 전 로컬 브라우저에서 열어 로그인 화면이 표시되고 콘솔 오류가 없음을 확인했다. 전송 아카이브 SHA-256은 `06c66649b5cae5582eed88f9573adb57afc15997aa4cacbed8562250197e24e3`이며 로컬과 NAS에서 일치했다.
- 운영 릴리스는 `/opt/haru-web/releases/t07-palette-auth-f96719b/web`이다. 기존 `haru-web` Compose 프로젝트의 웹 컨테이너만 교체했고, 컨테이너 상태는 `healthy`였다. 직전 정상 릴리스는 복구용으로 남겼다.
- 실제 `https://haruleaf.com/` 기본 주소를 인앱 브라우저에서 새로 불러와 로그인 상태의 기존 할 일 15/17개와 부산 여행 6/7개를 확인했다. 월간에서 여러 계획의 색상 띠를 육안 확인했다. 공개 CSS에는 승인한 다섯 HEX가 모두 들어 있다.
- 공개 HTML과 `/auth` 응답은 200, 비로그인 `POST /rest/v1/rpc/haru_snapshot`은 401이었다. 이 확인은 본인 로그인·기존 자료 표시 및 비로그인 차단을 각각 검증한 것이며, 전체 사용자·기기 환경의 무오류를 증명하지는 않는다.

실제 사용자 화면에서 색감이 시안과 다르면 브라우저에 표시된 계획별 합성색을 대조해 추가 보정한다. T07의 실제 5일 사용자 관찰·규칙 변경은 이 릴리스로 충족되지 않는다.
