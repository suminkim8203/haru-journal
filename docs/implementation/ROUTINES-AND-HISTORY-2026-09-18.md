# 루틴·기록 보존·배포 파일 검증

요약: 승인한 루틴과 배치/기록 편집 UI를 구현하고 NAS에 SQL 0008~0009를 적용했다. 실제 DB 검사·48개 회귀 검사·정적 빌드와 HTTP 검사를 통과했다. 공개 웹 앱 배포는 아직이다.

## 실제 구현

- 일반/루틴 계획 모두 기간 필수. 루틴 새 계획의 초기 날짜는 오늘부터 30일 뒤이며 사용자가 변경한다.
- 매일 반복 규칙, 시각 없이 반복/정해진 시각, 예상 시간·우선순위·설명·태그. 날짜마다 독립된 할 일을 저장하고 규칙/날짜의 중복을 DB 인덱스로 막는다.
- 반복 기간은 부모 계획 날짜를 기본값으로 사용하며 따로 편집할 수 있다. 밖으로 확장할 때 부모 기간과 이전 계획 이력을 같은 트랜잭션으로 보존한다. 자동 축소하지 않는다. 부모 직접 축소는 활성 규칙 범위를 포함해야 한다.
- 일간의 반복 할 일 수정은 이 날짜만/이 날짜부터 이후 반복을 선택한다. 이후 변경 전 수정·추가·기간 제외·보존 개수와 날짜/이유를 확인한다. 목록은 각 처음 50개, 개수는 전체 대상이다.
- 과거·완료·실행 이력(휴지통 실행 포함)·개별 수정·건너뛰기·중단 날짜를 이후 변경에서 보존한다. 이후 기간 제외와 중단/건너뛰기는 휴지통에서 복원한다. 제외했던 날짜를 기간 연장만으로 자동 재생성하지 않는다.
- 일반 계획 결과에는 루틴 발생을 섞지 않는다. 루틴 실제 시간은 일정/날짜별 시간 사용에 유지한다. 루틴 누적 완료 진행률은 추가하지 않았다.
- 예정 배치 수정/삭제와 종료 실행 수정/삭제 UI. 복원 시 기존 예정과 겹치면 사용자가 겹침을 확인해야 한다.
- 계획/할 일 삭제 때 실제 실행까지 숨기던 구현을 수정했다. 열린 실행은 같은 삭제 트랜잭션에서 종료하고 실제 실행·단상·회고는 유지한다. 삭제된 출처의 할 일은 지난 실제 기록/단상 날짜에서 읽을 수 있으며 변경 전에는 출처를 복원해야 한다.
- 기존 단상에 해당 날짜의 미삭제 실제 작업이 없을 때 읽기는 유지하며 편집은 제한한다. 새 단상은 실제 작업 날짜에만 작성한다.
- 처음 선택한 상세의 예정 시간·실행 기록·단상은 접힌다. 목록 접기는 네모 없는 아이콘, 접힌 상태의 펼치기는 28×42px의 가는 버튼이다. 기존 화면/필수 안내를 유지했다.
- 기록 시작 직후 화면의 1초 갱신 시각이 시작 시각보다 앞서 화면 오류가 발생하는 문제를 수정했다. 열린 구간은 첫 틱 전 0으로 계산하고 잘못된 종료 구간/겹침 검증은 유지한다.
- 계획 결과의 실제 값과 근거는 DB가 계산한 work_seconds를 동일하게 사용한다. 초가 있을 때 시간 표시에도 초를 남겨 실제−예상이 분 생략 때문에 어긋나 보이지 않도록 했다.

## 실제 NAS 검사

운영 DB는 PostgreSQL 17.6. 테이블 16개, snapshot schemaVersion 6, 공개 앱 함수는 haru_snapshot/haru_command/haru_export 세 개다. 관리 키를 앱에 이전하지 않았다. 내부 테이블/RPC 접근 경계는 그대로다.

0008~0009 전 /opt/supabase/backups/haru-before-routines-20260918/postgres.dump를 생성하고 pg_restore 목록을 검사했다. 적용 후 anon 역할의 트랜잭션에서 반복 3날짜 생성, 완료/건너뛰기/복원, 종료 기록/단상, 보호된 이후 변경, 반복 중단, 계획 삭제 후 기록 유지, 내부 접근 거절 및 지연 제약 검사를 수행하고 rollback했다. 다음 계획 생성과 개선점 복사도 anon 트랜잭션 검사 후 rollback했다.

검사 전후 exportedAt을 제외한 전체 내보내기 MD5는 1235446ea5895290cdf35b097b332a8b, revision 15로 같았다. 승인한 계획 1개·할 일 5개·종료 실행 3개·단상 1개·회고 1개를 유지했다. 새 루틴 예시를 운영 DB에 영속 업로드하지 않았다. 실패한 검사 요청은 원인을 보정하고 최종 검사를 다시 통과했다.

## 로컬 코드·화면 검사

- npm test: 48/48 통과. 반복 기간/ID/재시도/보호 대상/복원/겹침/보존/익명 권한, 최초 타이머 틱 및 시간 표시 회귀 포함.
- 일반 생산 빌드/타입 검사 통과 후, 최종 소스의 npm run build:static과 타입 검사 통과.
- 정적 HTTP 검사: 제호·공개 안내·JS 제공, 폐기한 저장 API·소스/환경 파일 경로 404. DB 쓰기 없음.
- 실제 앱 코드의 격리 복사 + 임시 로컬 SQL RPC/PGlite에서 브라우저 검사. 반복 규칙 편집→대상 확인→저장, 날짜별 일간, 상세 최초 접힘, 기록 시작/시간선 갱신/드래그, 기록 중 완료로 종료·버튼 제한·상세/포커스 유지, 배치 수정, 반복 중단→휴지통 복원, 개선점→새 계획→계획 표시 확인.
- 390×844 뷰포트의 문서 폭 375px, 화면 폭 390px으로 가로 넘침 없음. 기록 표시가 화면 안에 유지되고 종료 입력/저장과 28×42px 목록 펼치기 확인. 뷰포트 기본값 복원.
- 브라우저 검사 자료는 로컬 임시 DB에만 있다. NAS 증거로 확대하지 않는다. 배치 삭제의 브라우저 기본 확인 창은 자동화가 취소 처리하여 실제 확인→삭제 경로는 직접 렌더링 완료로 판정하지 않는다. 삭제·복원 데이터 경로는 SQL 검사로 확인했고 반복 중단·복원 UI는 직접 확인했다.

## 실제 백업 복구 검사와 한계

기존 설치 이미지 supabase/postgres:17.6.1.136로 네트워크 없는 별도 haru-restore-check-20260918 컨테이너를 생성했다(메모리 512MiB/CPU 0.5, 공개 포트 없음). 운영 DB를 덮어쓰지 않고 적용 전 백업의 journal 스키마와 공개 앱 함수 세 개를 pg_restore --exit-on-error로 복구했다. anon으로 snapshot 버전 4/계획 1/할 일 5/종료 기록 3/단상 1/회고 1을 조회하고 내부 테이블 직접 SELECT 권한 false를 확인했다. 검사 후 컨테이너 중지, 복구 검사 자료는 NAS에 유지한다.

이는 적용 전 프로젝트 자료/함수 복구 증거다. Supabase Auth/Storage/전체 플랫폼 복구, 최신 루틴 자료가 든 백업 복구, 정기 백업·VM 재부팅 복원·장비 부하 검사는 아직이다. 366일 시안 제한을 확정 서비스 조건으로 이식하지 않았고 아주 긴 반복 기간의 생성 성능/대량 화면/일괄 처리 범위는 검증하지 않았다.

## 스키마와 공개 배포 파일

[pds-schema-v2.json](../../contracts/pds-schema-v2.json)은 실제 NAS의 컬럼·제약·인덱스·트리거를 조회해 저장한 구조 메타데이터다. contractVersion 2와 snapshotSchemaVersion 6을 구분한다. 사용자 자료/키/비밀번호를 포함하지 않는다.

Next.js의 선택적 정적 export 설정과 build:static/preview:static을 추가했다. .next-static에 완성된 웹 파일을 생성하고 Git에서 제외한다. 일반 개발/빌드 경로는 유지한다. 실제 공개는 [배포 검토안](../deployment/WEB-RELEASE-REVIEW-2026-09-18.md)을 사용자 확인한 뒤 진행한다.
