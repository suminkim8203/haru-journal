# 실제 구현 데이터 계약 v1

상태: 승인된 제품 규칙의 구현 기준. 일반 계획/할 일 생성·완료의 첫 SQL 및 API는 구현·로컬 검증됐습니다. 아래 전체 모델과 실제 원격 DB 연결은 아직 완성되지 않았습니다. 실제 상태는 CURRENT_STATE.md를 참고합니다.

## 자료 모델

모든 자료는 하나의 diary_id에 속합니다. T06은 공개 단일 다이어리이며 계정/소유권은 T07에서 추가합니다. 날짜는 Asia/Seoul 달력 날짜, 시각은 UTC timestamptz, ID는 UUID입니다.

| 모델 | 핵심 관계와 제약 |
|---|---|
| diaries | timezone, revision. 성공한 쓰기마다 revision 증가 |
| plans | 일반/루틴 계획 모두 시작·종료 필수. 반복 규칙이 밖으로 늘어나면 부모 기간도 같은 저장에서 확장. 자동 축소 없음 |
| routine_rules | 반복 정의, 시작/종료 날짜, 중단일, 개정 이력 |
| tasks | plan_id, 선택적 routine_id/occurrence_date. 동일 규칙/날짜 중복 금지 |
| placements | task_id, 시작/종료. 종료>시작, 예정 겹침은 명시적 확인 |
| runs | task_id, 시작/종료/종료후보, source, 선택 blocked_reason(최대 2,000자), 출처 이름 스냅샷. 열린 실행은 diary별 최대 1개 |
| run_segments | work/pause/break/interrupt 구간. 겹침 금지, 마지막 구간만 열림 가능 |
| thoughts | task_id+date별 미삭제 1개, 본문 최대 4,000자. 해당 날짜에 실제 실행 존재 필요 |
| reflections | date별 미삭제 1개, 최대 4,000자, 빈 글 저장 금지, bookmarked. 계획 소속 없음 |
| reflection_sources | 가져온 단상 ID, 당시 본문/출처 스냅샷. 원문 변경은 회고에 전파하지 않음 |
| day_closures | date별 1개, closed_at. 회고 생략과 독립 |
| revisions | 수정 전 값과 시각. 실행 정정/글 수정 이력 보존 |
| trash_batches | 삭제 당시 대상 ID 목록, 삭제/복원 시각. 자동 만료 없음 |
| command_receipts | requestId, payload hash, 성공 응답, 결과 revision. 중복 쓰기 방지 |

모든 참조는 같은 diary 경계 안에서만 허용합니다. 삭제는 실제 기록을 cascade 삭제하지 않고 휴지통 표식을 사용합니다.

## 시간 계산

구간은 [시작, 종료). 실제 작업은 work 구간만 합산하며 pause/break/interrupt는 별도 보존합니다. 자정 경계에서 조회 날짜별로 잘라 집계합니다. 완료 체크와 타이머 종료는 독립입니다. 진행 시간은 저장된 시작/중단 구간과 현재 시각으로 재계산합니다. 종료 후보 시각은 저장 재시도 동안 유지합니다.

## 저장/충돌 처리

쓰기 요청: requestId(UUID), expectedRevision, command, payload.

1. 서버에서 형식·길이·날짜를 검증합니다.
2. DB 트랜잭션에서 diary 행을 잠급니다.
3. 동일 requestId의 성공 기록이 있으면 내용 hash를 검사해 기존 응답을 반환합니다. revision 검사보다 먼저 처리합니다.
4. 같은 requestId에 다른 내용이 오거나 현재 revision이 다르면 409로 거부합니다. 초안을 유지하고 최신 자료 확인 후 다시 적용하도록 안내합니다.
5. 삭제 상태, 유일성, 시간 겹침을 검증하고 관련 자료를 한 트랜잭션에서 저장합니다.
6. revision 증가와 성공 receipt를 함께 저장한 뒤 응답합니다. 실패는 전체 rollback합니다.

첫 구현은 diary 전체 revision을 사용하므로 서로 다른 항목 수정도 충돌할 수 있습니다. 공개 단일 다이어리의 안전한 저장을 우선하며 자동 덮어쓰기/내용 자동 병합은 하지 않습니다. 응답 유실 시 같은 requestId로 재시도합니다. 입력 초안은 서버 저장 성공과 구분합니다.

## 삭제/복원

계획 삭제는 소속 할 일/규칙/예정 배치를 묶어 휴지통으로 이동하고 실제 실행/단상/회고는 보존합니다. 실행 중인 항목이 있으면 먼저 종료를 안내합니다. 출처 이름은 스냅샷으로 보존합니다. 복원은 해당 batch의 삭제 표식이 일치하는 항목만 되살립니다. 별도로 삭제한 항목을 함께 복원하지 않습니다. 예정 겹침은 확인을 요구하고, 날짜별 회고/단상 충돌은 덮어쓰지 않고 거부합니다. 삭제된 소속 계획은 먼저 복원하도록 안내합니다.

루틴 변경은 이미 실행한 날짜를 덮어쓰지 않고 이후 범위에 적용합니다. T06 자동 영구 삭제는 없으며 30일 정책은 T07 검토 사항입니다.

## 구현 경로

예정 API: GET /api/diary, POST /api/commands, GET /api/export. Supabase 비밀키는 서버 전용이며 브라우저에 전달하지 않습니다. 테이블 직접 쓰기는 차단하고 검증하는 서버 경로를 사용합니다. API 자체는 승인된 로그인 없는 공개 편집 기능이며 접근 제한이 있는 개인 서비스라고 설명하지 않습니다.

구현 순서: 기본 조회/계획/할 일 → 시간 배치/실행 → 단상/회고/마무리 → 루틴/휴지통/집계 → 내보내기/통합검증.

내보내기는 schemaVersion, exportedAt, timezone, 사용자 자료/휴지통/수정 이력을 포함하고 비밀값 및 command receipt는 제외합니다. 기존 시안 자료는 자동 업로드하지 않습니다. 사용자가 선택한 파일을 검증하여 옮기고, 중복 ID/날짜·고아 참조·구형 메모/책갈피 스냅샷은 대응 표와 원본 보존을 먼저 준비합니다.

## 02.33 시안의 시간 분류 표시

표시 분류는 work(작업), break(휴식), interrupt(중단) 세 가지입니다. 기존 pause 구간은 표시/합계에서 interrupt에 더합니다. 내부 데이터는 기존 네 종류와 구간 경계/수정 이력을 유지하며 이번 변경으로 DB 마이그레이션이나 과거 기록 덮어쓰기를 하지 않습니다. 작업 시간 및 전체 경과 시간은 기존과 같습니다. 실행 기록의 휴식/중단 선택기와 미리보기도 같은 표시 규칙을 사용합니다. 이 시간 분류는 과제의 막힌 이유(C26)/막힘 수(C31)를 대신하지 않습니다.

02.34 재점검: 루틴을 plans의 종류로 유지하면서 기간을 비우는 시안/첫 SQL 규칙은 과제 C04(계획 기간 저장)에 맞춰 보정해야 합니다. 반복 규칙의 기간만 저장하는 것으로 계획 자체의 기간 저장을 충족했다고 설명하지 않습니다. 계획 기간 저장/반복 규칙 기간과의 관계는 보정안 결정 후 계약 및 SQL에 반영합니다. 이번 감사로 임의 DB 변경을 수행하지 않았습니다.

## 02.35 승인 보정 — 실제 DB 이식 전

- 실행 이유는 단상/회고와 독립합니다. 미입력 종료 가능, 수정 전 이유도 run 이력에 보존합니다. 기존 note를 자동 분류하지 않습니다.
- 같은 일반 계획·기간의 미삭제 할 일 중 미삭제 종료 실행의 현재 blocked_reason이 공백 외 내용을 가진 할 일을 한 번 셉니다. 완료한 일도 포함합니다. 초안·이력은 제외하며 근거도 같은 대상입니다. 루틴의 일별 발생을 일반 계획 집계에 포함하지 않습니다.
- plan_improvements: source_plan_id, source_plan_title 스냅샷, target_plan_id, text(최대 500자), source_text(전달 시 원본), created_at 및 수정 이력. 원본 계획/회고 수정·삭제가 복사한 문장을 변경하지 않습니다. 대상 계획의 성공 기준·목표를 덮어쓰지 않습니다.
- 같은 source_plan_id+target_plan_id+source_text 전달은 중복 추가하지 않습니다. 대상 문장을 수정해도 중복 기준 원문은 유지합니다. 새 계획 생성과 개선점 추가는 한 트랜잭션입니다. 실패하면 둘 다 저장하지 않고 초안을 유지합니다.
- 루틴 계획 생성은 오늘~한 달 뒤 기본값을 제공하고 직접 수정 가능합니다. 규칙의 기본 기간은 부모 기간을 상속하지만 독립 편집합니다. 밖으로 확장 시 계획/규칙 저장이 원자적으로 처리되고 변경 전 계획/처음 값은 보존합니다. 기존 활동/과거 항목을 덮어쓰지 않습니다. 직접 부모 축소는 현재 규칙 범위를 포함해야 합니다.
- 구형 빈 기간은 저장된 규칙/legacyPeriod의 실제 기록에서 복원합니다. 근거 없는 빈 묶음은 사용자 기간 설정이 필요합니다. 실제 첫 SQL의 루틴 날짜 NULL 제약은 아직 변경하지 않았으며 DB 이식 전 별도 마이그레이션이 필요합니다.

HTML 시안의 ID/저장 방식은 검토용입니다. 서버 스키마 적용·실제 DB 복원 검증 완료를 뜻하지 않습니다.

## 02.36 — 단상과 실행 이유의 저장 경계

실행 입력/수정은 blocked_reason을 변경하지만 기존 note를 새 단상으로 복사하지 않으며 정정으로 note를 덮어쓰지 않습니다. 단상 작성/수정은 task_id+date의 독립 경로에서 처리합니다. 이유 입력/초안 변경 자체는 저장이 아니고 명시적인 실행 저장/종료 시 저장합니다. 구형 동일 내용 단상의 표시 통합은 원문/이력/출처 ID를 보존하는 읽기 대응이며 DB의 자료 삭제와 구분합니다.

## 02.38 — 완료와 실행 종료의 원자적 처리

- 완료 명령은 동일 할 일의 열린 실행이 있으면 완료 상태·completed_at·실행 end·마지막 구간 end·선택 이유를 한 트랜잭션에서 저장합니다. 이미 고정한 종료 후보가 있으면 그 시각을 사용합니다. 실패 시 둘 다 rollback, 재시도는 같은 명령/종료 시각을 사용해야 합니다. 다른 할 일의 열린 기록은 변경하지 않습니다.
- 타이머 종료만으로 할 일을 자동 완료하지 않습니다. 완료 취소는 저장된 실행을 다시 열지 않습니다. 완료 취소 후 별도의 새 실행 시작 가능.
- 완료 상태에서는 타이머 시작 및 새/수정 시간 배치를 거부합니다. UI 차단만으로 판정하지 않으며 서버도 자료의 현재 상태를 검증해야 합니다. 수기 종료 실행 추가/정정·단상은 허용합니다. 기본 할 일 수정/삭제/완료 취소 기능은 유지합니다.
- 휴식/중단 구간은 전체 실행 범위 안에서 시작<종료 및 서로 겹치지 않음을 검증합니다. 분 단위 선택기는 전체 범위 안의 시각만 제공합니다. 전체 시간 변경 후 기존 구간을 자동으로 잘라내거나 시간을 추측하지 않으며 범위 밖 선택을 수정하도록 안내합니다.

HTML에 반영된 계약이며 실제 서버/SQL 구현은 후속입니다. 구형 완료+열린 기록 모순 자료는 실제 이식 전에 원문을 보존하고 대응 방식을 별도로 확인해야 합니다.

## 02.39 — 입력 방식과 저장 정밀도 구분

02.38의 분 단위 드롭다운은 폐기, 직접 입력/공통 시계로 변경합니다. 구간의 저장 형식과 범위/순서/겹침 검증은 동일합니다. 직접 입력과 기존 구간의 정확한 분을 유지합니다. 시계의 5분 간격 버튼 및 빠른 종료 5/10/15분은 편의 기능으로 원문 자동 반올림을 뜻하지 않습니다. 부모 실행 시각 변경에 따른 범위 밖 기존 값을 자동으로 잘라내지 않습니다.
