# 운영 준비 실행 순서

요약: 관리망 로그인이 복원되면 현재 NAS 설정을 먼저 읽고, 백업과 격리 복구를 검증한 뒤 자동 백업·재부팅 복원을 진행한다. 아래는 아직 실행 완료 기록이 아니다.

## 선행 점검

- 기존 Ubuntu VM의 Docker/Tailscale 자동 시작, Supabase와 haru-web 컨테이너 상태·재시작 정책, 현행 systemd timer/cron 백업 유무, 디스크 여유를 확인한다. 비밀 환경 파일 내용을 출력하지 않는다.
- 기존 DB와 볼륨·Studio 하위 경로 이미지·Envoy 인증/라우팅을 보존한다. 초기 설치/재초기화 스크립트를 실행하지 않는다.

## 백업과 복구

- NAS 내부 제한된 백업 디렉터리(700)에 일시별 백업을 생성하고 파일 권한 600을 적용한다. DB dump, 공개 RPC/역할·권한, 운영 설정 및 Storage 실제 사용 여부를 구분한다. 비밀번호가 포함되는 운영 설정 백업은 공개 Git/웹/출력에 넣지 않는다.
- pg_dump는 DB의 일관된 논리 백업이다. Storage 파일·컨테이너 설정·네트워크 경로는 별도 보존이 필요하다. 앱 내보내기만으로 전체 Supabase 복구를 보장하지 않는다.
- 백업의 크기·해시·복구 도구 목록 확인 후 네트워크가 차단된 별도 검사 DB에서 복구한다. 운영 DB 대상으로 restore를 실행하지 않는다.
- 프로젝트 자료 개수·집계·수정 이력·권한 및 스냅샷을 비교하고 검사 컨테이너를 종료한다. 실패한 경우 운영 서비스가 영향을 받지 않았는지 확인한다.
- 기존 예약 백업이 없으면 시간·디스크 소비를 고려해 예약을 구성한다. 기존 백업의 자동 영구 삭제는 임의로 추가하지 않는다. 같은 NAS 디스크 백업은 장비 전체 손실에 대한 별도 복제본이 아니다.

## 재부팅

재부팅은 해당 VM의 앱과 Supabase 서비스가 잠시 중단된다. 실행 직전에 사용자 사용 여부/중단 시간을 확인한다. 재부팅 후 컨테이너 상태·공개 앱/API/Studio 보호·DB 자료 및 집계를 비교한다. 실제 실행 전에는 재부팅 복구 완료로 표시하지 않는다.
