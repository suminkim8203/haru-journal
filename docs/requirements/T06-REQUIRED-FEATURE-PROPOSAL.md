# T06 필수 기능 보정 제안 — 1~4번 승인·02.36 저장 안내/단상 표시 보정

요약: 새 독립 화면을 추가하지 않고 실행 기록의 선택 이유, 계획 결과의 막힘 수, 다음 계획의 개선점 전달, 루틴 계획의 기간을 보정하는 안입니다. 사용자가 1~4번에 동의했습니다. 02.35 HTML 시안에 반영했으며 실제 React 앱/API/SQL 구현은 다음 단계입니다.

## 현재 단계와 범위

02.34 HTML 시안 및 실제 첫 저장 앱의 과제 충돌 보정 단계입니다. 과제 RULE의 C26/C31/C33/C04 및 관련 C08/C27/C83을 대조했습니다. 실제 React 앱은 일반 계획/할 일 생성·완료/완료 취소 범위입니다. 아래 기능의 최종 DB 연결/검증은 구현 후 확인해야 하며 문서만으로 제출 완료를 판정하지 않습니다.

단상(실행한 할 일·선택 날짜별 짧은 글), 회고(날짜별 하루의 글), 회고 책갈피, 독립 회고, 상세 기본 접힘, 누적 루틴 진행률/챌린지 제외 등 기존 합의는 유지합니다. 체크박스 잔여 깜박임은 실제 앱 브라우저 재현 항목으로 보류합니다. 서체/색감 전면 변경은 이번 제안에 포함하지 않습니다.

## 1. 실행별 ‘막힌 이유’ 선택 입력 — C26

추천: 막힌 이유는 실행 기록에 속하는 선택 입력 하나로 둡니다. 막혔던 일 별도 체크박스나 사유 관리 화면은 만들지 않습니다.

- 타이머 종료 확인의 ‘막힌 이유 · 선택’을 기본 접힌 영역으로 제공합니다. 미입력 상태에서 기록 종료 가능, 입력 시 같은 실행 저장에 포함합니다. 타이머 종료후보 시각은 입력 중에도 기존처럼 고정됩니다.
- 직접 실행 기록 입력/수정의 접힌 세부 영역에도 같은 입력을 제공합니다. 중단 구간이 없거나 완료한 할 일이어도 이유를 작성할 수 있습니다.
- 저장 후 일간 상세 → 실행 기록을 펼치면 해당 실행에 이유가 보입니다. 이유 없는 실행은 빈 문단을 표시하지 않습니다. 수정은 해당 실행의 기존 수정 기능에서 합니다.
- 예시: ‘자료를 찾느라 예상보다 오래 걸렸다.’ 시간 15분 멈춤 자체가 원인이 아니며 휴식했다고 자동으로 막힘 표시하지 않습니다.
- 단상은 자유로운 생각, 이유는 진행이 어려웠던 원인입니다. 기존 단상/구형 run.note는 이유로 자동 이동/분류하지 않습니다. 이유 입력은 단상/회고에 자동 복제하지 않습니다.
- 실제 앱에는 실행별 blockedReason을 별도 저장하며 수정 이력을 보존합니다. 계획 값은 덮어쓰지 않습니다(C27).

사용자 판단: 1번 동의 완료. 사용자 화면 피드백 반영.

## 2. 계획 결과의 ‘막힘’ 수 및 근거 — C31/C83

추천: 돌아보기 → 계획 결과의 기존 한 줄을 ‘계획한 할 일 / 완료 / 지연 / 막힘’으로 구성합니다. 별도 페이지/추가 목록은 만들지 않습니다.

- 같은 계획/마감 범위의 미삭제 할 일 중 현재 저장된 종료 실행에 비어 있지 않은 이유가 하나라도 있는 할 일을 한 번씩 셉니다. 실행별 여러 이유는 할 일 1개이며 공백만 입력한 이유는 세지 않습니다. 초안/저장 전 입력/수정 전 이력은 현재 숫자에 포함하지 않습니다.
- 완료한 할 일도 이유가 있으면 막힘에 포함합니다. 막힘은 미완료와 같은 뜻이 아니며 완료/지연/막힘을 더해서 전체 수를 만들지 않습니다.
- 숫자를 누르면 기존 근거 영역에서 대상 할 일 제목을 보여줍니다. 제목을 펼치면 관련 실행의 날짜/시간/이유를 그 자리에서 확인합니다. 이유 없는 실행을 모두 펼쳐 보여주지 않습니다.
- 예시: 한 할 일의 실행 3개에 이유 2개가 있어도 막힘은 1개입니다. 마지막 이유를 지우면 막힘에서 빠집니다. 할 일 삭제 시 같은 집계에서 빠지고 보존된 실행 자체는 별개입니다.
- 일반 계획 결과에 일별 루틴 발생 7개를 다시 끼워 넣지 않습니다. 일반 계획 대상이라는 표시 및 같은 대상의 정확한 개수/시간/근거를 유지합니다.

사용자 판단: 2번 동의 완료. 사용자 화면 피드백 반영.

## 3. 계획 결과에서 다음 계획에 개선점 한 줄 반영 — C33

추천: 돌아보기의 특정 일반 계획 결과 아래에 ‘다음 계획에서 바꿀 점’ 기본 접힌 영역을 둡니다. 회고와 분리하고 다음 계획의 별도 개선점으로 저장합니다.

- 여러 일반 계획 전체를 보고 있다면 기존 대상 계획 선택기 아래 ‘계획을 선택하면 다음 계획에서 바꿀 점을 남길 수 있습니다.’라는 짧은 안내를 둡니다. 특정 원본 계획 선택 시 작성 영역을 제공합니다.
- 구성은 개선점 한 줄 입력 → 대상 다음 계획 선택 → ‘다음 계획에 반영’입니다. 실행에 근거한 실제 개선점을 사용자가 작성하며 AI가 일반 단상/회고를 자동 변환하지 않습니다.
- 예시: ‘독서는 30분 대신 15분씩 나눠 배치하기.’ → 다음에 진행할 ‘10월 독서 계획’ 선택 → 반영.
- 대상은 원본과 다른 미삭제 일반 계획 중 사용자가 다음에 진행할 계획입니다. 임의의 날짜 순서만 보고 자동 연결하지 않습니다.
- 선택기에서 ‘새 계획 만들기’를 선택하면 버튼은 ‘다음 계획 만들기’가 됩니다. 기존 새 계획 입력폼을 그 자리에서 재사용하고 필수 계획 정보를 작성합니다. 계획 저장 시 개선점도 함께 저장하며 취소는 개선점 초안을 유지합니다. 별도 회고/보관함 페이지 방문은 필요하지 않습니다.
- 대상 계획 상세의 접힌 ‘이전 계획에서 가져온 개선점’에 문장과 출처 계획을 표시합니다. 반영 완료 안내에서 대상 계획을 바로 열 수 있습니다.
- 목표/성공 기준/기존 단상을 덮어쓰지 않습니다. 대상에 기존 개선점이 있으면 보존하고 새 출처 문장을 추가합니다. 동일 원본·대상·문장의 재시도는 중복 저장하지 않습니다.
- 전달 당시 문장을 저장하므로 원본을 이후 수정/삭제해도 대상에 남긴 문장은 유지합니다. 대상에서 문장을 수정하는 경우 해당 계획의 기록으로 수정 이력을 남깁니다.
- 하루 회고는 날짜별 독립 글로 유지하며 회고 → 다음 날 메모 연결 및 범용 ‘계획에 붙이기’는 되살리지 않습니다.

사용자 판단: 3번 동의 완료. 사용자 화면 피드백 반영.

## 4. 루틴 계획에 기간을 저장하고 필요하면 확장 — C04/C08

추천: 루틴 계획 생성폼에도 일반 계획과 같은 공통 달력의 시작일/종료일 한 줄을 둡니다. 각 할 일의 반복 기간은 기존처럼 유지하며 상위 계획 기간은 소속 루틴의 범위를 포함하도록 확장합니다.

- 생성 시 기본값은 오늘~한 달 뒤이며 사용자가 바꿀 수 있습니다. 부모 계획의 기간은 화면 계산값만으로 두지 않고 실제 계획 자료에 저장합니다. 일반 계획의 우선순위/성공 기준/예상 시간 및 원본 이력 필수 항목도 루틴을 계획으로 다루는 범위에서 유지합니다.
- 새 반복 할 일의 기본 반복 기간은 해당 계획 기간을 제시하되 할 일마다 직접 바꿀 수 있습니다. 같은 기간이라면 두 곳에 재입력하지 않습니다.
- 반복 시작일/종료일이 부모 계획 밖이면 저장 전에 입력 아래 ‘계획 기간도 09.01–11.30으로 늘어납니다.’처럼 변경 결과를 보여줍니다. 저장하면 루틴과 계획 기간을 함께 갱신합니다. 추가 확인 팝업은 만들지 않습니다.
- 예시: 부모 09.01–09.30, 독서 09.10–10.31 → 부모 09.01–10.31로 확장. 다른 루틴의 날짜/이미 실행한 날짜/과거 기록을 자동 변경하지 않습니다.
- 루틴 종료일을 줄이거나 삭제했다고 부모 기간을 자동으로 줄이지 않습니다. 부모 기간을 직접 줄이는 경우 현재 루틴의 반복 기간이 그 안에 들어가는지 검증합니다. 과거 실제 활동 기록은 기간 변경으로 삭제하지 않습니다.
- 자동 확장도 계획 변경이므로 처음 기간과 변경 전 값은 이력으로 보존합니다(C08). 계획 기간을 확장한 것과 루틴 규칙에서 미래 발생 항목을 생성/변경하는 것은 별개입니다. 기존 과거 발생 항목 보존 규칙을 유지합니다.
- 기존 기간 없는 루틴 계획은 저장된 반복 기간으로 근거 있게 기간을 채우는 대응안을 준비합니다. 반복 규칙도 없는 빈 묶음에 임의의 과거 기간을 만들지 않고 기간 설정을 받습니다. 02.35 시안은 저장된 기간에서 복원하며, 실제 DB 대응은 별도 마이그레이션으로 구현합니다.
- 화면에서는 루틴 계획 제목 아래 기간만 작게 표시합니다. 누적 완료율/100% 챌린지는 제공하지 않습니다. 이 기간은 관리 범위이지 실패를 확정하는 점수가 아닙니다.

변경 영향: 기존 ‘기간 없는 루틴 모음’에서 계획에 기간이 있는 구조로 바뀝니다. 자동 확장 안내 및 원본 이력이 필요합니다. 단순 날짜 입력 추가만으로 끝나는 변화는 아니므로 별도 판단이 필요한 항목입니다.

사용자 판단: 4번 동의 완료. 사용자 화면 피드백 반영.

## 승인 후 진행과 확인

1~4번 판단을 기록한 뒤 데이터 계약 보정 → HTML 시안 반영 → 02.36 저장 안내/단상 표시 보정 → 실제 앱/서버 저장 구현 순서로 진행합니다. 실제 앱 단계에서는 이유 저장/집계와 같은 근거의 일치, 개선점 전달 및 재시도 중복 방지, 계획 처음 값/이력 보존, 새로고침 복원, 브라우저 깜박임을 검증합니다.

이 네 항목 보정은 나머지 필수 기능/DB 연결/내보내기/공개 배포/보안 검증 완료를 의미하지 않습니다. 외부 평가 결과는 아직 확인되지 않았습니다.

02.36: 사용자가 나머지 보정 화면에 동의했습니다. 저장 절차와 단상 중복 표시 피드백을 보정했습니다. 자동 저장은 사용하지 않습니다.
