# 데이터 계약 v1 — 현행 승인 기준

요약: 아래는 구현해야 할 제품·저장 규칙입니다. 첫 저장 브랜치의 제한된 SQL/API와 구분하며 전체 모델·NAS 저장 완료를 뜻하지 않습니다.

## 공통과 필수 필드

모든 자료는 하나의 diary_id 경계에 속합니다. ID는 UUID, 날짜는 Asia/Seoul 달력 날짜, 시각은 UTC timestamptz입니다. 현재 값과 최초/수정 전 값은 구분해 보존합니다. T06 사용자 계정/소유권은 없습니다.

| 모델/개념 | 필드·관계·제약 |
|---|---|
| diaries | timezone, revision. 성공 쓰기마다 revision 증가 |
| plans | ID, 종류 general/routine, 제목, 시작·종료 날짜(둘 다 필수), 성공 기준, 우선순위, 예상 정수 분, 상태, 수정 이력 |
| tasks | ID, plan_id, 제목/설명, 마감 날짜, 우선순위, 예상 정수 분, 완료/시각, 선택 routine_id/occurrence_date, 수정 이력 |
| 할 일 태그 | ID, 이름, 할 일과 다중 연결. 중단 사유와 다른 개념. 로컬 0002의 tags/task_tags로 연결. 실제 NAS 적용은 별도 |
| routine_rules | 부모 계획, 반복 정의·시작/종료·중단일·개정 이력. 동일 규칙/발생 날짜 중복 금지 |
| placements | task_id, 시작/종료. 종료>시작, 예정 겹침은 명시적 확인 |
| runs | task_id, 시작/종료/종료 후보, source, 선택 blocked_reason 최대 2,000자, 출처 이름 스냅샷. diary별 열린 실행 최대 1개 |
| run_segments | work/pause/break/interrupt, 실행 범위 내 비중복 구간. 마지막 구간만 열림 허용 |
| thoughts | task_id+date별 미삭제 1개, 본문 최대 4,000자, 해당 날짜 실제 실행 필요 |
| reflections | date별 미삭제 1개, 본문 최대 4,000자, 빈 글 금지, bookmarked. 계획 소속 없음 |
| reflection_sources | 가져온 단상 ID와 당시 본문/출처 스냅샷. 원문 변경이 회고에 전파되지 않음 |
| day_closures | date별 1개, closed_at. 회고 생략과 독립 |
| plan_improvements | source_plan_id/title 스냅샷, target_plan_id, text 최대 500자, 전달 당시 source_text, 생성 시각·수정 이력 |
| revisions | 수정 전 값·시각. 실행 정정/이유/글 수정 이력 포함 |
| trash_batches | 삭제 당시 대상 ID 목록·삭제/복원 시각. 자동 만료 없음 |
| command_receipts | requestId, 동일 내용 판정값/요청, 성공 응답·revision. 중복 쓰기 방지 |

계획/할 일 우선순위는 기존 high/normal/low(높음/보통/낮음) 기준입니다. 계획 예상 시간은 독립 선언값으로 입력·보존합니다. 할 일 예상 합계가 계획 값을 자동 덮어쓰지 않습니다. 돌아보기 예상 합계에는 대상 할 일 예상만 더하며 상위 계획 예상과 중복 합산하지 않습니다. 근거는 [기존 상세 설계](archive/planning/core-data-design-v1.md)의 필드 정의와 계획 예상 규칙입니다.

## 루틴 기간과 변경

일반/루틴 모두 계획 기간 필수(C04). 루틴 기본은 오늘~한 달 뒤, 사용자가 편집 가능. 규칙은 부모 기간을 기본 상속하되 별도 편집합니다. 규칙이 밖으로 확장되면 부모 기간과 같은 트랜잭션에서 확장하고 변경 전 계획을 남깁니다. 자동 축소하지 않습니다. 직접 부모 축소는 현재 규칙 범위를 포함해야 합니다. 이미 실행한 날짜/과거 자료는 덮어쓰지 않고 이후 변경 범위를 적용합니다.

구형 빈 기간은 저장된 규칙/legacyPeriod 근거로 복원하며 근거 없는 빈 묶음은 사용자 기간 입력이 필요합니다. 첫 SQL의 routine 날짜 NULL 제약은 이 승인과 다르므로 적용 이력을 확인한 뒤 후속 마이그레이션으로 보정합니다.

## 시간·완료 처리

- 구간은 [시작, 종료). 실제 작업 합계는 work만 더합니다. 자정 경계에서 날짜별로 잘라 집계하고 겹침 중복을 허용하지 않습니다.
- 저장 구간은 네 종류를 보존하되 표시/시간 사용 합계는 작업(work)·휴식(break)·중단(pause+interrupt) 세 종류입니다. 중단 시간은 막힌 이유/막힘 수를 대신하지 않습니다.
- 진행 시간과 현재 시간 선은 저장 구간 및 현재 시각으로 재계산합니다. 종료 후보는 저장 재시도 동안 고정합니다.
- 완료 명령은 동일 할 일의 열린 실행이 있으면 완료 상태/completed_at, 실행 종료, 마지막 구간 종료, 선택 이유를 한 트랜잭션으로 저장합니다. 실패 시 모두 rollback, 같은 명령/종료 시각으로 재시도합니다. 다른 할 일의 기록은 변경하지 않습니다.
- 타이머 종료는 자동 완료가 아닙니다. 완료 취소는 종료 기록을 다시 열지 않으며 이후 별도 새 실행을 시작할 수 있습니다.
- 완료 상태에서는 타이머 시작·새 배치·배치 수정은 UI와 서버에서 금지합니다. 수기 종료 실행 추가/정정·단상·기본 할 일 수정/삭제/완료 취소는 허용합니다.
- 수기 실행/휴식/중단은 시작<종료, 부모 실행 범위 포함, 구간 비중복 검증. 전체 시간 변경 후 기존 구간은 보존하고 오류 수정 안내, 자동 잘라내기/반올림 없음.
- 입력은 직접 HH:mm/공통 시계. 5분 버튼과 경계/현재 정확한 분, 5/10/15분 빠른 종료는 편의 기능입니다. 긴 분 단위 드롭다운은 폐기했습니다. 자정 넘김은 날짜를 명확히 표시합니다.

## 이유·단상·회고·개선점

blocked_reason은 선택 입력이며 실행 저장/변경 저장/기록 종료에 함께 명시적으로 저장합니다. 입력 중 자동 저장하지 않습니다. 단상/구형 note를 새 이유로 자동 분류하거나 실행 수정으로 단상을 덮어쓰지 않습니다. 구형 동일 단상 표시 통합은 원문/출처/이력을 유지하는 읽기 대응입니다.

회고는 선택한 날짜 단상을 가져온 당시 스냅샷을 사용자가 수정해 저장합니다. 원문 변경/삭제가 저장 회고를 바꾸지 않으며 회고 삭제도 단상을 지우지 않습니다. 하루 마무리에서 회고 생략 가능, 빈 회고 생성 없음. 회고 클릭은 출처 계획 삭제와 무관하게 날짜 일간으로 이동합니다.

개선점은 계획 결과에서 다음 계획으로 전달하며 성공 기준/목표를 덮어쓰지 않습니다. source_plan_id+target_plan_id+source_text 중복 전달 없음. 대상 문장 수정 후에도 원문 중복 기준 유지. 새 계획 생성+개선점 추가는 원자적으로 저장하고 실패 시 초안 유지. 원본 계획/회고 수정·삭제는 복사 문장에 전파하지 않습니다.

## 집계와 근거

동일 일반 계획·기간·미삭제 대상 범위로 계획한 할 일/완료/지연/막힘/예상/실제/차이를 계산하며 모든 지표는 같은 대상의 근거로 이동합니다. 루틴 일별 발생을 일반 계획 집계에 섞지 않고 루틴 실제 시간은 일정/시간 사용에 보존합니다.

완료는 완료 상태, 지연은 서울 오늘 이전 마감의 미완료, 막힘은 미삭제 종료 실행의 현재 이유가 공백 외 내용을 가진 고유 할 일 수입니다. 완료한 일도 막힘에 포함할 수 있습니다. 초안/삭제/수정 전 이유는 현재 막힘 수에 넣지 않습니다. 이 세 숫자를 상호 배타적 분류나 총합으로 설명하지 않습니다. 예상은 대상 할 일 예상 합, 실제는 대상의 종료 실행 work 합, 차이는 실제−예상, 빈 대상은 0입니다. 근거도 동일 식·시간 범위·ID로 계산합니다.

## 저장·실패·충돌

요청은 requestId(UUID), expectedRevision, command, payload입니다. 서버 형식/길이/날짜 검증 → DB diary 잠금 → 같은 ID 성공 receipt의 내용 비교와 기존 응답 반환 → revision/상태/관계/유일성/시간 검증 → 원자적 저장과 revision/receipt 기록 순서입니다. 동일 ID 다른 내용 또는 오래된 revision은 409이며 자동 덮어쓰기/병합 없이 초안 유지·최신 확인을 안내합니다. 응답 유실은 동일 ID/내용으로 재시도합니다.

첫 구현은 diary 전체 revision이므로 다른 항목 수정도 충돌할 수 있습니다. 현재 입력 보호와 새로고침 후 초안 복원은 별도 구현 항목이며 구현 없이 보장하지 않습니다.

## 삭제·복원

계획 삭제는 소속 할 일/규칙/예정 배치를 묶어 휴지통으로, 실제 실행/단상/회고는 보존합니다. 할 일 삭제는 그 예정 배치도 휴지통으로 이동합니다. 실행 중이면 종료를 안내합니다. 출처 이름 스냅샷 보존, 실제 기록 cascade 삭제 없음.

복원은 batch의 삭제 표식이 일치하는 항목만 복원하며 별도 삭제 항목을 함께 되살리지 않습니다. 삭제된 소속 계획은 먼저 복원 안내. 예정 겹침은 확인, 같은 날짜 회고/단상 충돌은 덮어쓰지 않고 거부합니다. T06 자동 영구 삭제 없음, 30일 정책은 T07 검토입니다.

## API·내보내기·완료 증거

현재 앱은 브라우저 Supabase SDK에서 public.haru_snapshot()/haru_command()/haru_export()를 호출합니다. Next 저장 API는 제거했고 서버용 비밀키는 사용하지 않습니다. 공개 anon 키로 고정 다이어리의 제한된 함수를 실행하며, 내부 테이블·핵심 함수 직접 접근은 차단합니다. 이것이 T06의 사용자별 접근 제한을 의미하지 않습니다.

내보내기는 schemaVersion/exportedAt/timezone, 사용자 자료/휴지통/수정 이력 포함, 비밀값·command receipt 제외. 기존 시안 자료 자동 업로드 없음. 이식 시 원문 보존·ID/날짜 충돌·고아 관계·구형 스냅샷 대응부터 검증합니다.

contracts/pds-schema-v2.json은 실제 NAS 컬럼·제약·인덱스·트리거를 조회해 작성했습니다. contractVersion 2와 snapshotSchemaVersion 6을 구분합니다. 이 Markdown은 제출 JSON을 대체하지 않습니다. 최소 계획 1개/소속 할 일 5개/종료 실행 3개와 실제 DB 저장/복원·정상 집계를 검증해야 합니다.

## 2026-09-18 — 첫 계획/할 일 구현 대응

0002는 계획 priority, tags/task_tags ID 기반 다중 연결, 계획/할 일 수정 이력과 계획 이력 조회를 구현합니다. 태그 30자·20개 검증, 앞뒤 공백 제거·정확한 이름 중복 연결 없음. tags 누락은 유지·빈 배열은 해제이며 선택 필드 누락도 기존 값 유지입니다. 기존 자료 기본 priority=normal은 신규 보정값이고 원래 기록에 있던 값이 아닙니다.
