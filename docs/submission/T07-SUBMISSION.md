## 인증 구현 설명서

### ① 무엇으로 붙였나

NAS에서 운영하는 Supabase Auth v2.196.0과 앱의 `@supabase/supabase-js` 2.116.0을 사용했다. 이메일·비밀번호 가입, 6자리 이메일 확인 코드, 로그인·로그아웃, 로그아웃 상태에서 이메일을 통한 비밀번호 재설정을 제공한다. 앱은 로그인 뒤 토큰을 전달하고 서버는 현재 Auth 세션, 소유자, 기한을 확인한다. 접근 토큰은 발급 응답에서 3,600초였고 다이어리 접근 세션의 상한은 7일이다. 두 기한은 서로 다르다.

비밀번호 해시 생성·검증은 Supabase Auth의 bcrypt에 맡겼다. 같은 임시 비밀번호로 만든 시험 계정 A/B의 `auth.users.encrypted_password`가 모두 `$2a$10$`으로 시작하는 60자 값이면서 서로 다름을 읽기 전용으로 확인했다. 시험 계정의 원문 비밀번호는 제출물에 적지 않았다. 이 확인은 두 저장값이 서로 다르다는 증거이며, 저장값 전체 문자열의 제출 증거는 아직 없다.

### ② 왜 골랐나

기존 다이어리 데이터베이스가 Supabase에 있으므로 Auth의 계정 식별자와 자료 소유권 검사를 연결하기 쉬웠다. 비밀번호 저장과 이메일 코드 검증을 직접 구현하는 부담을 줄이고, 앱 서버의 접근 경계에서 세션 무효화와 계정별 자료 차단을 추가했다. 검토한 대안인 별도 Spring 인증 서버는 세션과 계정 동기화 운영을 추가해야 해서 이번 범위에서 선택하지 않았다. Google·Kakao 간편 로그인도 이번 과제의 필수 흐름이 아니어서 넣지 않았다.

### ③ 어디를 어떻게 고쳤나

| 흐름 | 사용자·서버 동작 | 소스 위치 |
|---|---|---|
| 가입·이메일 확인 | 사용자가 이메일·비밀번호를 입력하고 메일로 받은 6자리 코드를 입력한다. Auth가 계정과 코드를 검증한다. | `web/src/components/auth-form.tsx`, `web/supabase/functions/auth-guard/index.ts` |
| 로그인 | Auth가 자격 증명을 확인한다. 앱은 계정 상태를 확인한 뒤 본인 자료를 연다. 없는 이메일과 틀린 비밀번호는 같은 안내를 보인다. | `web/src/components/auth-form.tsx`, `web/src/components/private-journal.tsx` |
| 로그아웃 | 앱이 Auth 로그아웃을 요청하고 화면 상태를 비운다. 서버는 이전 세션으로 자료 요청을 거절한다. | `web/src/components/private-journal.tsx`, `web/supabase/staged-t07/01_session_boundary.sql` |
| 자료 조회·변경 | 서버가 로그인한 계정의 다이어리와 대상 계획·할 일·실행의 소유 관계를 확인한 뒤 읽거나 저장한다. 클라이언트가 적은 소유자 ID를 신뢰하지 않는다. | `web/src/lib/storage.ts`, `web/supabase/staged-t07/02_private_rpc_cutover.sql`, `03_private_read.sql` |
| 비밀번호 재설정 | 로그인 화면에서 이메일 확인을 거친 복구 세션만 새 비밀번호를 저장한다. 기존 세션의 다이어리 접근을 차단한다. | `web/src/components/auth-form.tsx`, `web/supabase/staged-t07/05_password_revocation.sql` |

현재 앱에는 로그인 상태의 별도 비밀번호 변경 화면, 초대 화면, 최초 비밀번호 설정 화면이 없다. 재설정의 `updateUser({ password })`는 이메일 복구 흐름에서 호출한다.

### ④ 안 열리는 것을 확인한 기록

아래 요청의 `Authorization`·`apikey`, 이메일·비밀번호·복구 코드는 증거 파일에서 가렸다. 응답은 검증에 필요한 필드만 남겼다.

1. **비로그인과 로그인.** 같은 `POST https://haruleaf.com/rest/v1/rpc/haru_snapshot`, 본문 `{}`. 비로그인 요청은 `401`, 로그인된 시험 계정의 요청은 `200`과 본인 `diaryId`·`planCount`를 반환했다. 첫 화면에는 로그인 화면이 표시되고 개인 기록은 보이지 않는다. [마스킹된 HTTP 기록](../t07/evidence/private-http-2026-09-22.json).
2. **로그아웃 전후의 동일 요청.** 같은 URL·메서드·본문과 같은 이전 토큰으로 로그아웃 전 `200`, 로그아웃 뒤 `401 {"code":"PT401","message":"Session expired"}`을 받았다. 토큰 문자열은 마스킹했다. [마스킹된 HTTP 기록](../t07/evidence/private-http-2026-09-22.json).
3. **계정 간 자료.** 시험 계정 A/B 각각 본인 계획 조회 `200`. A→B와 B→A의 계획 읽기는 모두 `404 {"code":"PT404","message":"Resource not found"}`. 양방향 수정(`update_plan`)·삭제(`delete_entity`)도 각각 `404`였다. 두 목록의 `foreignCount`는 0, 상대편 자료 스냅샷은 거절 전후 동일했다. [마스킹된 HTTP 기록](../t07/evidence/private-http-2026-09-22.json).
4. **비밀번호 재설정 뒤 이전 값.** 같은 이전 토큰으로 `POST /rest/v1/rpc/haru_snapshot`, 본문 `{}`를 요청했다. 재설정 전 `200`, 재설정 직후이며 로그아웃 호출 **전** `401 PT401`이었다. 옛 비밀번호 로그인은 `400 invalid_credentials`, 새 로그인 세션의 조회는 `200`이었다. 시험용 복구 코드는 내부 관리자 경로로 만들어 이 HTTP 검사가 실제 메일 전달을 검증한 것은 아니다. [마스킹된 HTTP 기록](../t07/evidence/password-reset-http-2026-09-23.json).
5. **탈퇴 유예 중 접근.** 시험 계정의 탈퇴 신청 `200 pending` 뒤 이전 세션 조회는 `401`, 재로그인 후 유예 상태의 조회·내보내기·계정 준비 요청은 `423 PT423`이었다. 명시적으로 취소한 뒤 자료가 유지됨을 확인했다. 실제 본인 계정은 탈퇴시키지 않았다. [마스킹된 HTTP 기록](../t07/evidence/deletion-http-2026-09-22.json).

주소·헤더·본문에 다른 계정 ID를 넣는 위조는 로컬 소유권 테스트에서 확인했다. 실제 HTTP 위조 요청·응답은 아직 별도로 남기지 못했다. 정상 수정·삭제 성공 요청도 양방향 거절과 나란히 제시할 별도 HTTP 기록은 없다. 저장 해시 전체 문자열, 로그인 요청·응답과 서버 로그 전체의 원문 부재, 실제 내보낸 파일 내용 역시 추가 확인이 필요하다.

### ⑤ AI와 나

- AI에게 맡긴 일: 인증 연결·자료 소유권 검사·화면 구현, 자동 검사와 요청·응답 증거 정리.
- 내가 직접 판단한 일: 기존 디자인 유지, 6자리 이메일 코드, 8자 이상·공백 없는 비밀번호, 계정 화면 분리, 탈퇴 7일 유예와 5일 자료의 질문·지표를 결정했다. 메일 수신·로그인·기존 자료 조회를 직접 확인했다.
- AI 말을 따르지 않은 일: 비밀번호 12자 이상 제안을 8자 이상으로 바꾸고, 로그인 중 별도 비밀번호 변경 UI와 본문에 끼어든 계정 조작 영역을 제거하도록 했다.

### ⑥ 아직 못 막은 것

브라우저에 지속 저장되는 인증값은 XSS가 발생하면 노출될 수 있다. 이메일 코드와 제한 로직만으로 분산 IP의 무차별 대입이 막힌다고 검증하지 않았다. 수동 외부 백업을 복구할 때 삭제 계정의 자료가 되살아나지 않도록 삭제 이력을 재적용하는 절차가 필요하다. 탈퇴 유예 168시간이 실제로 지난 뒤의 자동 삭제는 시간 경계 테스트와 달리 아직 현장에서 끝까지 관찰하지 못했다. 앞 항목의 미확인 HTTP·로그·내보내기 증거도 검증 한계로 남긴다.

## 5일 자료와 계획 사용 규칙

관찰 질문은 **“하루 계획에서 높은 우선순위 일반 할 일 하나를 먼저 골라 배치하면 하루 작업 시간이 달라지는가?”**이다. 지표는 하루 작업 시간, 단위는 분이다. Asia/Seoul 날짜별로 종료된 실행의 작업 구간을 합하고 휴식·중단·진행 중인 기록은 제외한다. 동일 기록은 한 번만 세고 누락은 0으로 대체하지 않는다. 이상값은 원자료를 확인해 유지하거나 정정 이력을 남긴다. 초 단위로 합산한 뒤 표시만 소수 첫째 자리로 반올림한다. 주 시작은 일요일이다.

과제 플랫폼의 `5일 관찰 시작` 입력란에는 아래처럼 각각 옮길 수 있다. 플랫폼에 지금 입력하면 플랫폼이 보관하는 시작 작성 시각은 **지금**이며 9월 23일로 소급되지 않는다.

| 입력란 | 입력 문구 |
|---|---|
| 5일 동안 답할 관찰 질문 | 높은 우선순위 일반 할 일 하나를 먼저 골라 배치하면 하루 작업 시간이 달라지는가? |
| 측정 지표 | 종료된 실행 기록의 하루 작업 시간 |
| 측정 단위 | 분 |
| 집계·계산 규칙 | Asia/Seoul 날짜별 종료 실행의 작업 구간을 초 단위로 합산한다. 휴식·중단·진행 중 기록을 제외한다. 같은 기록은 한 번만 세고, 누락은 0으로 대체하지 않는다. 이상값은 원자료를 확인해 정정하거나 유지한다. 합산 후 표시값만 소수 첫째 자리로 반올림하며 주 시작은 일요일이다. |
| 변경 전 계획 규칙 | 할 일을 고르는 기존 방식을 사용하고, 높은 우선순위 일을 먼저 배치하는 순서는 정하지 않는다. |

| 날짜 | 작업 | 예정 | 수기 입력한 실행 | 작업 시간 |
|---|---|---|---|---:|
| 9월 23일 수 | 비밀번호 재설정 뒤 이전 토큰 차단 결과 정리 | 09:06–09:46 | 09:11–09:43 | 32분 |
| 9월 24일 목 | 인증 구현 설명서와 확인 항목 검토 | 09:10–09:50 | 09:18–09:51 | 33분 |
| 9월 28일 월 | 시각 자산과 형광펜 시안 검토 | 09:03–09:43 | 09:06–09:45 | 39분 |
| 9월 29일 화 | 계획·일정 화면 사용성 검토 | 09:15–09:55 | 09:22–09:53 | 31분 |
| 9월 30일 수 | 일간 목록의 날짜 오류 확인 | 09:04–09:44 | 09:09–09:49 | 40분 |

2일차(9월 24일)와 3일차(9월 28일) 사이에 놓인 **규칙 변경 예시 시각**은 9월 27일 20:30이다. 변경 전에는 할 일을 고르는 순서를 정하지 않았다. 변경 후에는 높은 우선순위 일반 할 일 하나를 먼저 골라 첫 번째로 배치한다. 이유는 우선순위가 눈에 잘 띄지 않아 중요한 일을 뒤로 미루기 쉬웠기 때문이다. 1·2일차의 합계는 65분·평균 32.5분, 변경 뒤 3~5일차는 110분·평균 약 36.7분이다. 전체는 **175분=2시간 55분, 평균 35분**이다. Haru에서 이 계획만 선택했을 때 계획한 할 일 5개·완료 5개·예상 3시간 20분·실제 작업 2시간 55분을 확인했고, 다섯 수기 기록의 손계산과 일치했다.

이 다섯 오전 시각과 9월 27일 규칙 변경 시각은 사용자가 요청해 9월 30일에 사후 구성·입력했다. 일부 작업 주제는 실제 대화와 코드 이력에 근거하지만, 위 오전 실행·규칙 변경을 당시 실측한 것으로 확인하지 못했다. 플랫폼의 작성 시각도 9월 30일이다. 따라서 이 표는 앱 입력·집계 검증 결과이며 과제 원문의 ‘인증된 앱을 실제 5일 사용’했다는 증거로 제시하지 않는다.

## 짧은 확인 방법 4줄

1. 어디로 가나요: https://haruleaf.com/ 과 위 공개 T07 소스 주소를 연다.
2. 세 단계 안에 무엇을 하나요: 새 시크릿 창에서 로그인 화면 확인 → 설명서의 마스킹된 요청·응답 확인 → 로그인 전후·계정 간 접근 결과 비교.
3. 무엇이 보이면 통과인가요: 개인 자료는 로그인 전 안 보이고, 같은 자료 요청은 로그인 전 `401`·로그인 뒤 `200`, 다른 계정 자료 요청은 `404`다.
4. 안 될 때는 무엇이 보이나요: 인증되지 않은 자료 요청은 `401`, 남의 자료는 `404`, 탈퇴 유예 중 자료 요청은 `423`이다.

## AI와 내 판단 3줄

1. AI에게 맡긴 일: 인증과 소유권 검사 구현, 화면 연결, 테스트 및 가린 요청·응답 증거 정리.
2. 내가 직접 판단한 일: 디자인 유지, 이메일 확인 방식·비밀번호 조건·계정 화면·탈퇴 유예와 관찰 질문·지표 결정.
3. AI 말을 따르지 않은 일: 비밀번호 12자 조건을 8자로 조정하고 불필요한 로그인 중 비밀번호 변경 화면을 제거했다.
