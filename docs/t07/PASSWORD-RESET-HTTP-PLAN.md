# 비밀번호 재설정 이전 토큰 검증 — 실행 완료

요약: 실제 HTTP 증거 수집은 AI의 담당 작업이다. 사용자의 5일 기록 대기와 함께 멈출 이유가 없다. 다만 현재 사용 가능한 NAS 브라우저 콘솔의 도구 정책은 비밀번호 변경을 사용자가 직접 실행하도록 요구한다. 사용자가 NAS에서 준비한 스크립트를 실행했고, 2026-09-23 17:47 KST 실제 요청 검사가 통과했다.

## 준비된 검사

`scripts/verify-password-reset-http.py`를 NAS에서 `python3 <파일> --run`으로 실행한다. 실제 사용자 계정을 조회·변경하지 않는다.

1. 별도 시험 계정과 임시 비밀번호를 메모리에서 생성한다.
2. 공개 로그인 API로 로그인하고 다이어리 snapshot 200을 저장한다.
3. 내부 Auth 관리자 API로 시험 계정의 recovery 코드를 만든다. 메일 발송 검사는 이 절차에 포함하지 않는다.
4. 공개 `/auth/v1/verify`와 `/auth/v1/user`로 복구 인증 및 새 비밀번호 저장을 수행한다.
5. **로그아웃을 호출하기 전에** 원래 토큰·주소·메서드·본문 그대로 snapshot을 요청해 401인지 확인한다. 비밀번호 재설정 효과와 로그아웃 효과를 혼동하지 않는다.
6. 이전 비밀번호 로그인 거절, 새 비밀번호 로그인 성공, 원래 다이어리 자료 불변을 확인한다.
7. 시험 세션 로그아웃 후 `/tmp/haru-password-reset-http.json`에 비밀값을 가린 결과만 저장한다. 시험 계정은 자동 영구 삭제하지 않는다.

비밀번호·OTP·서비스 키·토큰은 파일이나 콘솔에 출력하지 않는다. 실패할 때도 예외 메시지 원문 대신 단계와 예외 종류만 기록한다. 스크립트는 `--run` 없이 동작하지 않는다. 구문 검사 및 실제 NAS 실행 완료. [마스킹된 HTTP 증거](evidence/password-reset-http-2026-09-23.json)에 요청 6개를 보관했다.

## 실행 이후

AI가 결과를 회수해 요청/응답을 검토하고 설명서·진행 기록에 반영한다. 실패라면 원인을 수정하고 재검증한다. 사용자가 본인 비밀번호·인증번호·토큰을 채팅에 제공할 필요가 없다.

## 확인한 결과

- 재설정 전 snapshot 200 → 복구 인증 200 → 비밀번호 저장 200 → **로그아웃 전** 같은 토큰 snapshot 401(`PT401`, `Session expired`). 주소·메서드·본문·토큰이 동일하다.
- 이전 비밀번호 로그인 400(`invalid_credentials`), 새 비밀번호 로그인 후 snapshot 200. 동일 다이어리의 빈 시험 snapshot이 보존됐다. 실제 사용자 자료 보존 검사와 구별한다.
- 발급 토큰의 expires_in은 3600초였다. 7일의 DB 세션 접근 상한과 별개다.
- 정리: 이미 무효인 이전 토큰의 로그아웃 403, 복구 세션·새 로그인 세션의 로그아웃 각각 204. 실제 사용자 계정 변경 없음.
- 응답은 비밀값을 제거한 선택 필드다. 관리자 API로 복구 코드를 생성했으므로 이번 검사는 메일 수신이나 브라우저 전체 조작 증거를 대신하지 않는다.
