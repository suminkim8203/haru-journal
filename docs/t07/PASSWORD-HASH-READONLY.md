# T07 시험 계정 비밀번호 저장 확인 — 2026-09-23

요약: 운영 Auth DB의 **폐기 가능한 기존 시험 계정 두 개**를 읽기 전용으로 확인했다. 두 계정은 같은 임시 비밀번호를 사용해 생성됐지만 저장된 해시 2개는 서로 다르다. 본인 계정의 비밀번호·해시는 조회하지 않았다.

## 자료 출처와 관찰

- 기존 2026-09-22 시험 스크립트는 아래처럼 임시 비밀번호를 한 번 생성해 시험 계정 A/B의 Auth 관리자 생성 요청에 같은 값으로 사용했다. 원문 비밀번호를 출력·저장하지 않았다. 당시 작업 스크립트는 개발 PC의 `D:/workspace/T06-palndosee/work/verify-private-http.py`에 있으며 공개 저장소의 제출 증거는 이 문서와 마스킹된 HTTP 기록이다.

  ```python
  password = secrets.token_urlsafe(24)
  for label in ['A', 'B']:
      # 두 계정 생성 요청 모두 같은 password 변수를 사용
      ...
  ```
- [양방향 접근 확인 기록](evidence/private-http-2026-09-22.json)의 시험 계정 ID `8d1040a5-…`, `8591e1c9-…`만 대상으로 NAS의 `auth.users.encrypted_password`를 읽었다. 변경 명령은 실행하지 않았다.
- 두 행 모두 저장값이 `$2a$10$`으로 시작하고 길이가 60자였다. `count(*) = 2`, `count(distinct encrypted_password) = 2`, 최소/최대 길이 모두 60자였다. 두 저장값의 뒤쪽은 서로 달랐다. `$2a$` 접두사는 bcrypt 해시 형식이고 `10`은 비용 값이다.
- 이 확인은 원문이 DB에 그대로 저장되지 않았고 같은 비밀번호가 계정마다 서로 다른 해시로 저장됨을 보여준다. 화면·응답·로그 전체에 원문이 전혀 없다는 검사는 이 DB 조회만으로 입증되지 않는다.

## 구현 방법과 한계

- 해시 생성·검증 주체는 앱 자체 코드가 아니라 설치된 Supabase Auth다. [Supabase 공식 비밀번호 보안 문서](https://supabase.com/docs/guides/auth/password-security)는 `auth.users.encrypted_password`에 bcrypt 해시와 계정별 무작위 salt를 저장한다고 설명한다. 현재 두 행의 접두사·길이·상이한 값은 그 설명과 일치한다.
- 과제 C103에 제출할 시험 계정 저장값의 **전체 문자열**은 아직 별도 증거 파일로 옮기지 않았다. 화면상 접두사·길이·상이함을 확인한 단계다. 실제 사용자 해시를 제출 증거에 사용하지 않는다.
- C105–106 로그인 요청·응답·서버 로그·브라우저 화면의 비밀번호 원문 부재는 별도 점검이 필요하다. 이 문서만으로 완료 처리하지 않는다.
