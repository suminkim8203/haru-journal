# 계획 탐색·종료 상태 검토 — 2026-09-29

요약: 사용자는 모든 계획을 하나의 선택기에 넣는 계획 페이지를 불편하게 느꼈고, 2026-09-29 상태 구분·목록 탐색·월간 완료 수·색 순환 및 편집·드래그 시간 수정에 동의했다. 로컬 코드와 SQL 마이그레이션을 작성하고 검사했으며, 운영 적용 여부는 별도 배포 기록으로 확인한다.

## 확인한 현재 구현

- 계획 페이지는 `plans.tsx`의 단일 `<select>`에 모든 계획을 나열한다. 상태별 계획 검색·분류·페이지네이션이 없으며, 선택한 계획 제목 위에 항상 `진행 중`이라고 쓴다.
- 일반 계획 모델에는 독립된 완료·종료 상태와 종료 시각이 없다. 할 일 완료 비율은 현재 할 일 상태로 계산한다. 일간의 `완료한 계획 N개 보기`는 모든 일반 할 일에 `completed_at`이 있고 선택한 날짜가 마지막 완료 다음날일 때만 기본 목록에서 접는다.
- 월간 기간 띠 색은 계획 ID 해시로 5색 중 하나를 계산한다. 생성 순서별 배정이나 사용자의 색 선택값을 저장하는 기능은 없다.
- 월간 상세에는 현재 완료율이 있지만 달력 띠에는 완료 수가 없다.
- 0분 예상 할 일을 타임라인에 드래그하면 기존 확인창은 1분으로 바꿔 저장했다. 실제 서비스에서 1분 배치가 화면에 존재함을 확인했다. 로컬 수정은 시간을 편집 가능하게 하고 0분 예상이면 30분을 먼저 보여주며 저장 전 조정하도록 안내한다. 이 수정은 아직 운영 배포하지 않았다.
- 로컬 수정 후 타입 검사·기존 기능 검사 73개·프로덕션 빌드가 통과했다. 빌드에는 실제 인증 연결값 대신 컴파일 검사용 임시 값을 사용했으므로 이 결과물을 배포하지 않는다. 기존에 저장된 1분 배치의 수정·삭제는 사용자의 기록을 임의 변경하지 않기 위해 수행하지 않았다.

## 승인한 결정과 구현 방식

1. **계획의 종료와 할 일 완료를 분리한다.** 일반 계획의 실제 완료 수는 할 일 체크 수로 계산하고, 직접 종료는 별도 시각 `closed_at`으로 남긴다. 직접 종료해도 `6/7 완료`처럼 실제 수를 그대로 보인다. 모든 할 일이 완료되면 다음 날부터 일간 기본 목록에서 접고, 종료일이 지난 미완료 계획도 별도 묶음으로 접는다. 루틴은 이 종료 방식에 넣지 않는다. 직접 종료 후 새 할 일·배치·타이머 시작은 서버에서도 거절하며 과거 실행 기록 수기 보정은 허용한다. 잘못 종료한 경우 다시 열 수 있다.
2. **계획 페이지의 탐색을 목록형으로 바꾼다.** 진행 중 계획을 먼저 보여주고, 완료·기한 경과 계획은 접힌 묶음으로 둔다. 각 행은 계획명·기간·완료 수/전체 수와 상태를 보여주고 선택하면 기존 계획 상세로 이동한다. 계획명 검색과 상태 필터를 넣는다. 페이지네이션은 항목이 많아진 뒤 필요할 때 도입한다. 월간은 기간의 시각적 개요, 계획 페이지는 찾기·수정·종료·할 일 관리로 역할을 나눈다.
3. **월간의 완료 수**는 계획명 옆 또는 띠 밖의 읽기 쉬운 위치에 `6/7`처럼 표시하고, 백분율은 기존대로 상세에만 둔다. 긴 제목·여러 띠·모바일 7열에서 실제 배치를 먼저 확인한다.
4. **월간 형광펜 색**은 생성 순서에 따라 다섯 색을 순환하고 `marker_color`를 DB에 저장한다. 삭제나 정렬 변경으로 기존 계획 색이 바뀌지 않는다. 계획 수정에서 색을 별도로 바꿀 수 있다. 기존 계획에는 생성 시각·ID 순으로 색을 배정한다. 현재 ID 해시 방식은 운영 SQL 적용 뒤 제거된다.
5. 월간 상세의 완료한 할 일에 붙는 `완료 ·` 문구는 사용자가 **유지**하기로 했다. 취소선도 유지한다.

## 과제 기준

T07은 최종 T06 다이어리에 인증을 이어 붙이는 과제다. T06 제출 당시 공개·무로그인 조건은 T07에서 로그인·개인 자료 보호로 대체된다. 그 외 계획/할 일 관리, 실행 기록, Plan–Do–See 연결, 돌아보기 집계·근거, 다음 계획 개선점, 실제 DB 저장·복원, 내보내기 등은 화면 구조를 바꾸더라도 제공해야 한다. T06의 특정 메뉴 위치·토글·선택기 모양을 그대로 유지할 필요는 없다. T07의 실제 5일 사용과 3일차 전 계획 **사용 규칙** 변경은 UI 변경과 별개다.

## 5일 규칙 용어

고정 지표는 하루 실제 작업 시간(분)이며 계산 규칙은 5일 내내 같아야 한다. 바꿀 것은 관찰·계산 규칙이 아니라 사용자가 하루 계획을 세우는 행동 규칙 하나다. 우선순위 점 표시처럼 화면만 바꾸는 것은 행동 규칙 변경의 증거가 아니다. 실제 관찰 1일차가 확정되지 않아 변경 시각·전후 비교는 아직 없다. 후보 규칙을 바꿀 경우 질문도 1일차 전에 함께 고정하고, 2일차 뒤·3일차 전에 실제 변경 시각·이유를 남긴다.
