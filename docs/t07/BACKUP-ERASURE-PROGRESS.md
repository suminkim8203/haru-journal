# 백업의 탈퇴 자료 삭제 — 진행 기록

요약: 사용자는 탈퇴 유예 7일이 끝나면 백업 사본의 해당 기록도 제거하기를 요구했다. 기존 7일 운영 DB 삭제만으로 이 요구를 완료했다고 판단하지 않는다.

현재 작업 순서: 사본 위치 조사 → 개인 계정 방식의 백업·복구 검사 보정 → 격리 DB에서 대상 계정만 제거/다른 기록 불변 확인 → 백업 파일 재생성 및 복구 확인 → 예약 삭제와 통합 → 실제 증거 및 UI 안내 갱신.

2026-09-22 확인:
- 자율 진행 지침은 AGENTS.md에 이미 저장되어 있다. 작은 단계가 끝날 때 최종 답변으로 멈추지 않고, 실제 사용자 입력/필수 승인 또는 해결 불가 차단까지 계속한다.
- 정기 HDD 백업뿐 아니라 배포 전 DB 사본·과거 JSON snapshot·복구 시험 컨테이너가 존재한다. 원본 내용을 외부로 전송하지 않고 경로·크기 목록만 조사했다.
- 기존 백업/복구 코드는 인증 없이 공개 RPC를 호출하는 T06 방식이었다. 관리자 전용 journal 행 수·서명 대조 방식으로 변경했다. 실제 새 백업 /backup/haru-operations/20260922T082854Z 생성 성공, 전후 상태 동일.
- 새 백업의 postgres/_supabase 격리 복구 종료 코드 0. journal 대조값 불일치가 발생해 검증을 중단했고 원인을 조사 중이다. 복구 완료로 보고하지 않는다. 운영 DB는 변경하지 않았다.
- erase-offline-account.sql은 격리 복구 사본에서만 사용한다. 삭제 대상 외 journal 행을 전후 비교해 변화가 있으면 트랜잭션을 취소한다. 로컬 검사 통과. 원본 백업 자동 재작성과 예약 작업 통합은 아직 미완료.

계정 탈퇴의 168시간 경계와 실제 모든 사본 정리 완료 시각은 구분한다. 파일이 실제로 제거/재생성되고 재검증되기 전에는 백업 삭제 완료로 기록하지 않는다. VM 스냅샷·장비 외부 백업처럼 이 앱이 관리하지 않는 사본의 존재와 처리 범위는 별도 확인 대상이다.

후속 확인: 표준 정렬(C collation)과 UTC로 비교 기준을 고정하니 변경 이력 두 테이블이 일치했다. 새 백업 20260922T084427Z를 격리 복원하여 postgres 및 _supabase 복구 성공, journal 19개 테이블 행 수/내용 일치, 익명 접근 제한 유지, 복원 컨테이너 정지를 확인했다. 로컬 전체 검사 69/69 통과.

격리 삭제 후속: 시험 계정만 제거한 복구본에서 다른 journal 행 불변을 확인했다. prepare-sanitized-backup.py로 원본 dump를 유지한 새 사본을 만들고 재복원하여 19개 테이블 일치를 확인했다. 이는 미리보기 검증이며 자동 원본 교체는 비활성이다. 배포 전 독립 dump는 추가 복원 오류를 조사 중이므로 전체 사본 삭제 완료로 판단하지 않는다.

## 2026-09-23 최신 상태 — 백업 정리 자동화 및 안내 배포

요약: 관리 중인 백업의 계정별 정리 작업을 NAS 예약 작업에 연결했고, 서비스 안내도 배포했다. 실제 168시간 경과 관찰과 모든 외부 사본 검증을 완료한 것은 아니다.

- 백업 작업 설치, timer active, 최초 실행 success. 설치 당시 만료 계정 0건으로 운영 계정 삭제나 원본 백업 교체는 없었다.
- 격리 복구 사본에서 대상 계정 제거 후 다른 journal 기록 불변 및 재복원 일치를 확인했다. 전체 작업 시험은 폐기 가능한 사본에서 만료 시각과 운영 계정 조회를 대역 처리했다. 6개 파일 처리, 반복 실행 변경 0건. 원본 백업과 운영 자료는 변경하지 않았다.
- 관리 범위: /backup/haru-operations, /opt/supabase/backups, /backup/haru-archive-preview 및 지정된 격리 시험 사본. 알려진 DB dump·journal SQL·다이어리 snapshot을 재생성한다. 알려진 중지 상태 복구 컨테이너도 정리한다.
- 백업과 삭제는 같은 잠금으로 직렬 실행한다. 대상 외 journal 행이 달라지거나 복원이 실패하면 완료로 기록하지 않는다. 외부 삭제 이력은 복구 후 재적용을 위해 별도로 유지한다.
- 웹 release t07-backup-dc86e5cb8684 적용. 공개 HTML/JS/CSS 등 19개 파일이 빌드와 일치한다. DB 변경 없음. 화면에는 추가 백업 유예기간 없음과 장애 시 지연 가능성을 표시한다.
- 이전 대조 오류는 정렬 규칙과 시간대 차이였다. C 정렬·UTC 기준 새 백업의 19개 journal 테이블 일치를 검증했다. 로컬 69개 검사, 타입 검사, 비공개 정적 빌드 통과.

한계: Proxmox 스냅샷·외부 장비 사본의 존재와 삭제 연동은 현재 확인되지 않음. 새로운 이름/형식의 백업을 자동으로 모두 식별한다는 보장은 없다. 운영 감사 로그나 물리 디스크 잔존 영역의 완전 삭제를 검증한 것이 아니다. 임의의 수동 복구는 서비스 재개 전 외부 삭제 이력을 재적용해야 한다. 실제 7일 관찰은 아직이며 T07 전체 완료로 판정하지 않는다.
